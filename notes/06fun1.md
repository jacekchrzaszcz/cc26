## The language

### Lfun --- what is new

```
Type ::= int | bool | Callable[[Type, ...], Type]
exp  ::= ... | exp(exp, ...)
stmt ::= ... | return exp
def  ::= def var(var: Type, ...) -> Type: stmt+
Lfun ::= def... stmt...
```

From Python's `ast`, free again:

```
Call(func, [arg, ...])
Return(value)
FunctionDef(name, args, body, ...)
```

### A program is a list of functions

`shrink` gains a second job:

```
Module([def..., stmt...])   ==>   [def..., main]

main = def main() -> int:
           stmt...
           return 0
```

`main` stops being a special case: it is *the function called
`main`*.

### Mutual recursion

```python
def is_even(n: int) -> int:
    if n == 0: return 1
    else: return is_odd(n - 1)

def is_odd(n: int) -> int:
    if n == 0: return 0
    else: return is_even(n - 1)
```

`is_even` calls a function defined after it --- so names and arities
are collected **after `shrink`, over the whole module**:

If there is no typechecker, we may at least check if the argument count is right.

## The calling convention

### What callq does --- and what it does not

`callq f` pushes the return address and jumps. That is all.

It does **not**:

1. pass the parameters,
2. build or remove a frame,
3. protect any register from the callee.

Those three are the *convention*: an agreement between two pieces of
code that never see each other. We now write both sides of it.

### Parameter passing

```
rdi  rsi  rdx  rcx  r8  r9
```

in that order; the result in `%rax`.


What if there is more than six arguments?

- usually they go on the stack, before the return addres
- The EoC book uses tuples - we will discuss this later

### The frame

![](call-frames.svg)

The stack grows down --- top to bottom is *decreasing* address, and
the order the instructions run in.

The space below return address is ours; above it is the caller's.

Every offset we
emit is measured from `%rbp`.

**Note:**

- in x86_64 ABI (gcc etc), params that do not fit in registers come before return addr
- initially we limit parameters to 6; then lift this limitation using tuples
- 32-bit x86 passes parameters only on the stack

### Caller/callee-saved registers liveness


- **caller**: assume all nine caller-saved registers are destroyed ---
  a value live across a call needs a callee-saved one;
- **callee**: push what you use, pop it in the conclusion.

When computing liveness:

```
Callq(f, n)   R = the first n argument registers
              W = all nine caller-saved registers
```

Written for `input_int`; describes `callq my_fun` just as well.

**A direct call needs no new instruction and no new liveness case.**

### Stack alignment

At a `callq`, `%rsp` must be 16-byte aligned. On entry it is 8 (mod
16) --- the return address --- and `pushq %rbp` brings it back to 0.

So everything pushed *after* `%rbp` must total a multiple of 16:
callee-saved registers and spill area **together**.

```python
def frame_padding(self, stack_used, base):
    return -(base + stack_used) % 16
```

Get it wrong and nothing fails --- until a call into the runtime
crashes inside `printf`.

### remove_complex_operands

**`Call`** is complex, and its arguments must be atoms:

```python
print(add(input_int(), 2))   ==>    _1 = input_int()
                                    _2 = add(_1, 2)
                                    print(_2)
```

Not much different from `print(input_int() + 2)`

### return argument does not need to be atomic

So function call is not new. Return is.

```python
case Return(value):
    new_value, temps = self.rco_exp(value, False)
```

Same treatment as an `if` test, similar reason:

```python
    return (42 if x > 41 and x < 43 else 44)
```

An attempt to simplify it to `_1` will introduce redundant assignments;
if we keep the complex condition, `explicate_control` will handle it nicely:

``` att
block.0:
    movq $44, %rax
    jmp answerp_conclusion
block.1:
    movq $42, %rax
    jmp answerp_conclusion
block.2:
    cmpq $43, %rdi
    jl block.1
    jmp block.0
answerp_start:
    cmpq $41, %rdi
    jg block.2
    jmp block.0
```

### return input_int() ?

What about function calls?

``` python
def echo():
    return input_int()
```

if we keep the return's argument complex, we get

``` att
echo_start:
    callq input_int
    jmp echo_conclusion
```

This can be optimised further, but it's good enough for now.

### Tail position

An expression is in **tail position** when its value is the
function's result. `explicate_control` gets a fourth position
function:

```python
explicate_tail(e, basic_blocks) -> list[stmt]
```

Three cases:

```python
case IfExp(test, body, orelse):     # each branch returns on its own
case Begin(body, result):           # statements, then a tail
case _:                             # return e
```

And in `explicate_stmt`:

```python
case Return(value):
    return explicate_tail(value, basic_blocks)   # cont is dropped
```

Note there is no continuation here - nothing runs after a `return`.

The book's `explicate_tail` has a fourth case: a call in tail
position.<br/>
We skip it in the base version, you can implement it as one of the extensions.

### if f(x) --- already done

A call returns a value, so it can be a condition:

```python
if is_even(n):
    print(1)
```

And a call is **not an atom** --- it cannot sit in the condition of a
jump.

`explicate_pred` already handles it: lecture 4's last case binds any
non-atomic condition to a variable and asks again.<br/>
Written that way,  it covers a
form that did not exist when it was written.

**No change to `explicate_control` for this.** Worth checking, not
worth coding.


### fib, explicated

```python
def fib(n: int) -> int:
    if n < 2:
        return n
    else:
        return fib(n - 1) + fib(n - 2)
```

``` python
def fib(n):
  block.0:
      return 0
  block.1:
      return n
  block.2:
      _1 = (n - 1)
      _2 = fib(_1)
      _3 = (n - 2)
      _4 = fib(_3)
      return (_2 + _4)
  fib_start:
      if n < 2:
        goto block.1
      else:
        goto block.2
```

- **`block.0` is dead**: the implicit `return 0`, built before we knew
  every path returns. Same as `while True:`.
- **`return` carries a full expression**, not an atom ---
  `return (_2 + _4)`. RCO left it complex on purpose.

## select_instructions

### The call

```
lhs = f(a1, ..., an)    =>   movq a1, %rdi
                             movq a2, %rsi
                             ...
                             callq f
                             movq %rax, lhs

return atm              =>   movq atm, %rax
                             jmp f_conclusion
```

A return is *an assignment to `%rax`, then a jump* --- so one helper
compiles both. Two callers.

The conclusion label is the current function's; that is all
`main_conclusion` ever was.

### The parameters

A definition loses its parameters and gains moves at the top of its
start block:

```python
def add(x: int, y: int) -> int:
    return x + y
```
translates to
```att
add_start:
    movq %rdi, x
    movq %rsi, y
    movq x, %rax
    addq y, %rax
    jmp add_conclusion
    ...
```

Now `x` and `y` are ordinary variables and the rest of the compiler
needs to know nothing about parameters at all.

### Why not just use `%rdi`?

Saving parameters prevents problems with `%rdi` etc being caller-save, consider

```python
def bad(x):
  print(x)
  return (x+1)
```
If you "just use `%rdi` for x", the call to print can overwrite it.

```att
bad_start:
  callq print        # x is already in %rdi
  movq %rdi, %rax    # ?? probably garbage now
  addq $1, %rax
  jmp bad_conclusion
```
with argument saved, the allocator can do (almost) a good job:

```att
good_start:
    movq %rdi, %rbx
    movq %rbx, %rdi
    callq print_int
    movq %rbx, %rax
    addq $1, %rax
    jmp good_conclusion
```
The annoying `movq %rbx, %rdi` can be eliminated using peephole optimisation; it's no big deal.

### add, all the way down

```att
	.align 16
add:
    pushq %rbp
    movq %rsp, %rbp
    jmp add_start

add_start:
    movq %rdi, %rcx
    movq %rsi, %rdx
    movq %rcx, %rax
    addq %rdx, %rax
    jmp add_conclusion

add_conclusion:
    popq %rbp
    retq
```

`main` is the same shape, with `.globl` in front of it (other functions do not need to be global).

`add` is a leaf: its parameters die before any call, so they get
caller-saved registers and the prelude saves nothing.

`.align 16` ensures the address of `add` is divisible by 16.<br/>
Not strictly necessary now, but may come handy later.

### Silly register walks

Register allocation can sometimes emit stuff like

```att
    movq %rdi, %rcx
    movq %rsi, %rdx
    movq %rcx, %rax
    addq %rdx, %rax
    jmp add_conclusion
```
well executed move-biasing can help here and instead produce

```att
    movq %rdi, %rax
    addq %rsi, %rax
    jmp add_conclusion
```

This is not easy, even GCC sometimes emits such silly moves<br/>
However `movq reg, reg` is cheap, so don't sweat it.

### Prelude and conclusion, per function

Unchanged code, called once per definition:

```att
f:
    pushq %rbp
    movq  %rsp, %rbp
    pushq <each callee-saved register the colouring used>
    subq  $<padded spill area>, %rsp
    jmp   f_start
...
f_conclusion:
    addq  $<padded spill area>, %rsp
    popq  <them back, in reverse>
    popq  %rbp
    retq
```

Lecture 4 made the conclusion a block every finishing path jumps to.
Here we see why it is useful.

Need to restore callee-saved regs is the reason we do not use `leave` (or `movq %rbp, %rsp`).

### fib: what it was all for

```att
fib:
    pushq %rbp
    movq %rsp, %rbp
    pushq %rbx
    pushq %r12
    jmp fib_start

fib_start:
    movq %rdi, %r12
    cmpq $2, %r12
    jl block.1       # base case
    jmp block.2      # recursive case
```

`n` lives in `%r12` --- callee-saved, because it is still needed after
the recursive calls.<br/>
The prelude saves only the registers the
colouring used: two pushes after `%rbp`, 16 bytes, frame is
aligned.

### Across the call

```att
block.2:
    movq %r12, %rcx      # we need n later
    subq $1, %rcx        # n-1
    movq %rcx, %rdi      # move-biasing would prefer %rdi
    callq fib            # %r12 survives
    movq %rax, %rbx      # fib(n-1), needed later
    movq %r12, %rcx         
    subq $2, %rcx        # n-2
    movq %rcx, %rdi
    callq fib            # %rbx survives
    movq %rax, %rcx
    movq %rbx, %rax
    addq %rcx, %rax
    jmp fib_conclusion
```

`%rbx` holds the first result across the second call. `%rcx` is
caller-saved and is reused freely --- every value in it dies before
the next `callq`.

Remember call-live variables? They go in callee-save registers.

## Move biasing helps again:

```att
# --no-move-bias            # --move-bias
block.2:                    block.2:
    movq %r12, %rcx             movq %r12, %rdi
    subq $1, %rcx               subq $1, %rdi
    movq %rcx, %rdi             callq fib
    callq fib                   movq %rax, %rbx
    movq %rax, %rbx             movq %r12, %rdi
    movq %r12, %rcx             subq $2, %rdi
    subq $2, %rcx               callq fib
    movq %rcx, %rdi             movq %rax, %rcx
    callq fib                   movq %rbx, %rax
    movq %rax, %rcx             addq %rcx, %rax
    movq %rbx, %rax             jmp fib_conclusion
    addq %rcx, %rax
    jmp fib_conclusion
```

The final `move, move, add` dance is not easy to get rid of. One way is to use `leaq`:

```att
    leaq (%rbx, %rax), %rax
```
But again, register-to-register moves are cheap.

## Wrapping up

### Summary

- **`shrink` gathers the top level into `main`** --- after it, a
  program is only definitions.
- **`callq` does very little.** Parameters, frames, register
  protection: convention, and now ours on both sides.
- **A direct call is `Callq(f, n)`** --- the node we already had.
- **`explicate_tail`** is additional explicate variant; `return` discards its
  continuation.
- **The parameters are saved to variables in prelude** - then handled by allocator
- **The back end became a loop**: same passes, per-function state.

Next time: tuples, and the garbage collector that has to find them.

Then functions again --- as values, with tail calls, and with more
than six arguments.

## Extra material

### How deep can we go?

Every call costs a frame. Ours are 16 bytes, so an 8 MB stack takes
us about half a million deep --- `is_even(400000)` prints,
`is_even(800000)` segfaults.

CPython gives up at 1000, long before we do.

So the point of tail calls is not depth. A loop written as tail
recursion should cost **no** stack; ours costs a frame per
iteration.

### What the functions lecture skips wrt the book

Not next time --- tuples come first, because one of these three needs
them.

*Functions as values.* `reveal_functions`: `Name(f)` becomes
`FunRef(f, n)` --- **complex**, because it is the source of a `leaq`.
Then `leaq f(%rip), lhs` and `IndirectCallq(fn, n)`.

*Efficient tail calls.* `TailCall`, `TailJump`, and the conclusion
inlined before an indirect jump. Self-contained once parameters are
capped at six --- so this one does *not* wait for tuples.

*More than six arguments.* `limit_functions` packs arguments 7…n into
a tuple.

## Implementation hints

### ast.FunctionDef

Python `ast` defines a `FunctionDef`, but it represents a Python function:

```
FunctionDef(name, args, body, decorators, returns, ...)
```

One wrinkle: `FunctionDef.args` is an `ast.arguments` object --- with
`posonlyargs`, `kwonlyargs`, `vararg`, `kwarg`, `defaults` --- not the
list of pairs the book's figures show. Flatten it, and reject
everything we do not implement.

### shrink

```python
for statement in module.body:
    match statement:
        case ast.FunctionDef():
            defs.append(self.shrink_def(statement))
        case Import() | ImportFrom():
            pass
        case _:
            main_body.append(statement)
defs.append(FunDef('main', [], main_body + [Return(Constant(0))]))
```

and reject a source function actually called `main`, before it
silently replaces ours.

`shrink_def` is where `ast.arguments` gets flattened:

```python
if args.posonlyargs or args.kwonlyargs or args.vararg or args.kwarg \
        or args.defaults or args.kw_defaults:
    raise NotImplementedError(...)
params = [a.arg for a in args.args]
```

### Two errors worth raising

```python
case Call(Name(f), args) if f in self.function_arity:
    if len(args) != self.function_arity[f]:
        raise ValueError(f"{f}() takes {self.function_arity[f]} "
                         f"argument(s), {len(args)} given")

case Name(id) if id in self.function_arity:
    raise NotImplementedError(
        f"{id} is a function; using one as a value needs first-class "
        f"functions, which this stage does not have")
```

The first is the mistake students actually make. The second is the
hole we are leaving --- say so, or it compiles to a garbage read.

Both must come **after** `input_int`/`print`.

### Definitions, twice

A definition's body is a *list of statements*, then a *dictionary of
blocks*. Two small dataclasses, not one reused `ast.FunctionDef`, so
`body` means one thing per pass:

```python
FunDef(name, params, body)          # in cfun.py
CFunDef(name, params, blocks)
X86Def(name, blocks)                # in x86_ast.py
```

Give each a `__str__`: `-vv` is most of the debugging here.

### One helper for assignment and return

```python
def select_assign(self, dst, rhs):
    """Compute rhs into dst.  Shared by assignment and return, which
    differ only in whether the destination is a variable or %rax."""
```

`return f(x)` then leaves a `movq %rax, %rax`, which
`patch_instructions` already deletes.

### One counter, program-wide

`temp_counter` must *not* become per function: `generate_name` feeds
temporaries **and** block labels, and after `flatten` every label
lives in one dictionary.

Leave it on the compiler; let `flatten` assert no label is defined
twice.

### The conclusion label has no block yet

Liveness runs *before* `prelude_and_conclusion`, so `jmp f_conclusion`
points at a label that does not exist in the block dictionary yet:

```python
self.block_live(definition.blocks.get(label, []), label)
```

An empty block has an empty live-before set, which is the right answer
--- `%rax` is reserved and never allocated.

### Stretch goals

- **Move biasing.** Colour `movq s, d` so `s` and `d` share a register
  when they do not interfere --- the parameter moves then vanish.
- **Dead blocks.** `fib` leaves one; so does `while True:`. Remove what
  is unreachable from each `_start`.
- **A type checker.** `Callable[[int], int]` is the only new type.
